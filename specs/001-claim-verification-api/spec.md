# Feature Specification: Claim Verification API (Structured Judgments)

**Feature Branch**: `001-claim-verification-api`  
**Created**: 2025-10-17  
**Status**: Draft  
**Input**: User description: "这是一个用于事实验证的工具，可以通过 API做自动化调用。这个工具接收一个结构化或是自然语言的事实描述，输出一个结构化的判断。该判断可以是 yes/no的二元判断，也可以是 0-1这样的对于事实性的一个连续判断。这个判断必须伴随理由和论据。这个工具应该依赖大模型的能力和网络搜索来给出判断，优先判断质量而不是反应时间或是 token节约。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提交自然语言事实并获取结构化结论 (Priority: P1)

作为API调用方，我希望提交一段自然语言的事实陈述（如“公司A在2024年Q4营收同比增长超20%”），以便系统返回结构化判断（yes/no 或 0-1连续分数），并附带理由与可点击证据来源。

**Why this priority**: 这是最常见的集成入口，能直接产出业务可用的事实核查结论。

**Independent Test**: 通过调用单一接口提交一句自然语言陈述，验证响应中包含结论、理由、至少一个证据链接及引用片段。

**Acceptance Scenarios**:

1. **Given** 提供明确、可验证的陈述，**When** 提交请求，**Then** 返回二元结论或连续分数，并包含≥1条证据（链接+摘录）与简明理由。
2. **Given** 证据不足，**When** 提交请求，**Then** 返回“不可判定/未知”并说明原因（如“权威来源不足”）。

---

### User Story 2 - 提交结构化事实对象以支持批量与一致性 (Priority: P1)

作为API调用方，我希望提交一个结构化的事实对象（包含主题、断言、时间范围等关键字段），以获得更可控的一致性输出与易于比对的字段化结果。

**Why this priority**: 结构化输入便于后续自动化审计、对比与溯源。

**Independent Test**: 通过提交结构化载荷，验证响应字段与输入字段一致对齐，且证据、理由与结论齐备。

**Acceptance Scenarios**:

1. **Given** 含有主题、断言、时间范围的结构化输入，**When** 提交请求，**Then** 返回结构化判断对象，字段齐全、类型正确。
2. **Given** 输入缺关键字段，**When** 提交请求，**Then** 明确报错并指明缺失字段。

---

### User Story 3 - 获取连续0-1评分与可解释理由 (Priority: P2)

作为API调用方，我希望在需要时获得0-1的连续真实性评分（同时可选获取二元结论），并查看简明、可复核的理由与证据引用。

**Why this priority**: 连续评分支持置信度排序、阈值策略与灰度决策。

**Independent Test**: 对同一陈述多次调用，验证评分与理由稳定性在可接受区间内（小幅波动，不改变主要结论）。

**Acceptance Scenarios**:

1. **Given** 明确可验证陈述，**When** 请求连续评分，**Then** 返回[0,1]区间数值、二元结论（可选）与证据。
2. **Given** 模糊或表述不清陈述，**When** 请求评分，**Then** 返回低分并说明不确定来源（如定义模糊、时间范围不清）。

### Edge Cases

- 含糊/范围不清：未给出时间或地理范围导致歧义。
- 冲突证据：来源之间相互矛盾时的裁决策略与输出说明。
- 不可访问来源：目标页面不可达、反爬限制或需要付费墙内容。
- 语言混杂：中英文交叉、专有名词翻译差异导致检索偏差。
- 实时性：陈述涉及“最新/当前”的时间点解释与证据时间戳一致性。
- 法规合规：部分站点ToS/robots限制导致证据不足的处理策略。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须接收两类输入：自然语言陈述或结构化事实对象（包含主题、断言文本、时间范围可选字段）。
- **FR-002**: 系统必须输出结构化判断对象，至少包含：结论类型（binary/continuous）、二元结论（yes/no/unknown）、连续分数[0,1]、理由要点（2-5条）、证据列表（URL+引用片段+标题/来源名）。
- **FR-003**: 证据链必须可复核：每条证据提供可点击链接与原文摘录，能对应到结论中的具体要点。
- **FR-004**: 当证据不足或存在重大歧义时，系统必须返回“unknown/不可判定”，而非强行给出yes/no。
- **FR-005**: 默认以质量优先：允许较高延迟以换取更高的判断准确性与更完整的证据链；不得以降低质量换取更短响应时间。
- **FR-006**: 输出必须包含用于审计的元信息（如生成时间、输入摘要、证据数量、判定理由摘要），以便线下复核。
- **FR-007**: 支持中英文陈述；若无法可靠处理的语言，返回“unknown”并解释语言支持限制。
- **FR-008**: 对同一输入在短期内的重复调用，结论与分数应具一致性（允许小幅波动但不应改变主要结论）。
- **FR-009**: 二元与连续判断可同时提供；若调用方指定其一，系统按照指定返回。
- **FR-010**: 来源优先级遵循权威与注册表数据优先的原则；当仅有一般网页来源时，需要在理由中注明其可信度限制。
- **FR-011**: 明确不在本功能范围内：构建人工标注后台、长期数据存储/报表、用户身份体系（除非另行定义）。
- **FR-012**: 安全与合规：不得违反来源站点ToS与robots规范；在证据不足时以“unknown”优先于规避规则。

不明确处（限3项，需产品决策）：

- **FR-013**: 连续分数[0,1]语义定义为“真实性概率”（经校准）：建立标准基准集与周期性校准机制（例如每季度），使分数具可解释性、跨任务可比性与阈值可用性。
- **FR-014**: API访问控制采用API Key模式（按账户/项目分配）；所有请求必须携带有效密钥；配额与审计按Key维度执行。
- **FR-015**: 证据来源与最低条数：至少1个权威来源；若仅有一般新闻/博客来源则允许返回但必须在理由中标注“可信度有限”；当无权威来源且证据冲突/不足时返回“unknown”。

### Key Entities *(include if feature involves data)*

- **Claim（陈述）**: 主题、断言文本、可选时间范围/地域、语言、备注。
- **Judgment（判断）**: 结论类型（binary/continuous）、二元结论（yes/no/unknown）、连续分数[0,1]、理由要点、审计元信息。
- **Evidence（证据项）**: URL、标题/来源名、摘录片段、抓取时间、可选可信度标签。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95%请求返回包含“结论+理由+≥1条证据（URL+摘录）”的完整结构化响应。
- **SC-002**: 在一套外部标注的测试集上，正确率≥80%（以二元结论对齐为准；连续分数与阈值0.5一致性≥80%）。
- **SC-003**: 对“证据不足”的样本，误判为“有结论”的比例≤5%；“unknown/不可判定”的场景均附带原因说明。
- **SC-004**: 90%请求在可接受等待时间内完成（例如≤30秒），且不以牺牲证据完整性为代价；当无法满足时，提供部分结果与原因说明。
- **SC-005**: 100%响应包含可审计元信息，可被下游流程记录与复核。
